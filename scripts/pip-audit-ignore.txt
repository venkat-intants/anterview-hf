# --- python-jose + ecdsa: GONE, not accepted -------------------------------
# Both blocks that lived here are DELETED because the dependency is.
# `python-jose` was removed on 2026-10-06 in favour of PyJWT, and with it the three
# packages it alone pulled in — `ecdsa`, `pyasn1`, `rsa`. So:
#
#   * CVE-2026-85394 (algorithm confusion: a DER public key accepted as an HMAC
#     secret) is FIXED, not suppressed. PyJWT rejects bare DER — but only from
#     2.14.0; 2.13.0 accepts it exactly as jose did, verified by forging a token
#     against it. The floor is `^2.14` in every pyproject.toml for that reason, and
#     the exact pin is 2.15.1.
#   * PYSEC-2026-1325 (`ecdsa`, Minerva-class timing attack) is GONE from the images
#     entirely — `ecdsa` was `Required-by: python-jose` and nothing else.
#
# They are deleted rather than left as entries with a note, because
# `scripts/audit_python_deps.sh` passes every id in this file as `--ignore-vuln`: an
# entry for a package nobody installs is a live suppression waiting to hide something
# real.
#

# PYSEC-2026-1845 is gone: all four services now pin pytest 9.0.3 with

# the plugin bump with it). Every suite passes on 9.0.3 — see the PR.

# --- starlette — FIXED 2026-10-03 -------------------------------------------
# All seven ids are gone: PYSEC-2026-161, -248, -249, -1941, -1942, -2280 and
# -2281 are patched in starlette 1.3.1, which all four services now pin
# alongside fastapi 0.133.0 (0.115.14 capped starlette below 0.47).
#
# ONE OF THE SEVEN WAS GENUINELY REACHABLE, and it is worth recording which,
# because the next person to weigh a starlette advisory should know the shape
# that mattered: PYSEC-2026-249 — request.form() silently ignores max_fields
# and max_part_size for application/x-www-form-urlencoded. That is an
# UNAUTHENTICATED event-loop DoS (~1,000,000 fields in a sub-10MB body blocks
# the worker for seconds; one 50MB field forces matching memory), and
# POST /apply/{requisition_id} takes Form fields pre-auth. The
# rate_limit("public_apply_submit", 6) in front of it bounded the rate, not the
# cost of a single request.
#
# The other six were not reachable, each for its own reason, all re-checked
# against the code on 2026-10-03 rather than inherited:
#   - PYSEC-2026-161 / -248 (Host header and leading-slash-less path poison
#     request.url.path / .hostname): the previous review left this UNVERIFIED
#     and flagged it as the one to look at hardest, because the consoles are
#     separated by path behind Caddy. CHECKED AND CLEAR: no authorization
#     decision anywhere in services/ or shared/ reads request.url. The only
#     path read is shared/http_observability.py::_route_label, which takes the
#     MATCHED ROUTE TEMPLATE off scope["route"] for a metrics label — not the
#     reconstructed URL, and not for any decision.
#   - PYSEC-2026-2281 (StaticFiles UNC SSRF): Windows-only, and StaticFiles
#     appears nowhere in services/ or shared/. Production is Linux containers.
#   - PYSEC-2026-2280 (HTTPEndpoint attribute dispatch): needs an HTTPEndpoint
#     subclass registered through Route(...) without methods=. Every route here
#     is a FastAPI decorator, which always constrains the method.
#   - PYSEC-2026-1941 / -1942 (FileResponse Range DoS): FileResponse appears
#     nowhere in services/ or shared/.
#

# langgraph-sdk, CVE-2026-104873 (HIGH, 2026-10): the resource-scoped
# authorization decorators @auth.on.threads / .assistants / .crons ignore their
# `actions=` argument and register the handler for EVERY action on the resource,
# so an authenticated user can bypass the fallback ownership check and read or
# delete another user's resource.
#
# NOT REACHABLE HERE, and the reason is structural rather than a judgement about
# our handlers: those decorators exist for a LangGraph **API server**
# deployment, and we do not run one. `langgraph_sdk` is never imported anywhere
# in services/ or shared/ — grep finds no `langgraph_sdk`, no `auth.on`, no auth
# handler of any kind. We use langgraph as a library: the graph is built and
# compiled in-process (`build_graph(llm).compile()`,
# interview_core/app/graph/build.py). The package is here only because langgraph
# depends on it.
#
# Unblock is the same migration as the cluster above, and it is a hard version
# wall rather than caution: langgraph==0.2.76 pins `langgraph-sdk<0.2.0,>=0.1.42`
# so 0.4.4 cannot be installed beside it, and langgraph-sdk 0.4.4 itself requires
# `langchain-core>=1.4.0` against our pinned 0.3.86 (checked against PyPI
# metadata 2026-10-06). Mirrored in .trivyignore: it is HIGH with a fix
# available, so the image scan sees it too.
CVE-2026-104873
